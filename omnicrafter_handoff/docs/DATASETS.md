# Dataset definitions: names are not sufficient identifiers

## Vocabulary

A **2ref3 set** is one logical sample: two clean reference RGBs, three target
camera poses, three clean target RGBs for supervision/scoring, and three noisy
renders for cleanup conditioning. That is five camera views but up to eight RGB
file references (2 refs + 3 GT + 3 noisy). A black query is created online and
does not replace/delete the stored noisy render.

Two manifest formats coexist:

- **Legacy panorama JSONL:** one row per target; three adjacent rows with the
  same `source_sample` form one 2ref3 set. Some 2ref1 manifests retain
  `original_source_sample` / `original_target_number` so the triplet can be rebuilt.
- **Current mixed JSONL:** one row per complete 2ref3 set, with `references` and
  `targets` lists and embedded world-to-camera poses. 200,000 lines = 200,000 sets.
- **Evaluation JSON:** `sets` is a list of complete groups. The frozen benchmark
  includes poses/calibrations, seeds, original GT paths, metric GT paths and priors.

Do not use line count alone to compare dataset sizes. A `scene_name` can denote
a trajectory/sequence folder, not an entire physical building or a unique mesh.
“Train” identifies samples allowed to update weights; “val/test” identifies held
out samples for scoring. Our conversational use of “HM3D test” usually means the
generated **HM3D official-validation-scene benchmark**, not the hidden HM3D test split.

## Three generations to keep separate

| Dataset identity | Size / meaning | Where it is used |
| --- | --- | --- |
| Legacy `5input_model` train | 249,000 2ref3 sets each of HM3D, Replica, JHU, 360Loc; 996,000 total | Early Model 2 training and dataset-specific continuations |
| Legacy `5input_model` val | 1,000 2ref3 sets per dataset; 4,000 total | Early baseline/model tests; **not** the later Replica204 benchmark |
| Current mixed train | 100,000 DL3DV + 60,000 HM3D + 40,000 JHU entries | Current perspective/panorama run; **no Replica or 360Loc** |
| Current panorama evaluation | HM3D423 + Replica68 + JHU500 2ref3 sets | Teacher, recent OmniCrafter and current mixed-model comparisons |
| Current perspective evaluation | DL3DV2,800 2ref3 sets | Current mixed-model comparisons |

The old 5input split is a deterministic sample split. It does not automatically
guarantee unseen scenes or unseen reference pairs. Prior Replica experiments
found that only **284 of the old 1,000 sets had reference pairs unseen in that
training split**. Do not apply this 284-set number to Replica204, and do not call
all old validation sets scene-held-out. Preserve the exact audited subset when
reporting that historical result.

## HM3D

### Training

Processed source data live in two `HM3D_Bi_data*` trees (see address catalog).
The common `5input_model/HM3D` copy contains model-facing **512×256 W×H ERP RGB**
and stored noisy point-cloud renders. Poses are separately indexed by
`5input_model/poses/manifest.json`. The training-only manifest
`manifests/hm3d_train.jsonl` represents 249,000 groups / 747,000 target rows.

The current mixed run takes **60,000 groups without replacement**, with
deterministic scene/sequence-balanced quotas across **3,552 sequence folders**:
16 or 17 groups per folder. These are not 3,552 distinct HM3D physical scenes.
The original panorama-only balanced 2ref3 mixture instead uses **232,424 HM3D
groups + 232,424 JHU groups**. These are different training manifests.

The original preprocessing turns scene meshes and navigable camera trajectories
into posed panoramic RGB/depth, then creates reference-conditioned noisy renders.
For reproducing this training run you need the already processed RGBs, noisy RGBs
and poses—not GLB/OBJ assets, Habitat, radial depth or point maps at training time.
Do not assume every old stored training render was generated by PanoVGGT merely
because current cleanup evaluations use PanoVGGT.

### New validation / evaluation

`hm3d_val_data` follows the released Splatter360 evaluation identities:
**423 trajectories from 85 HM3D validation scenes**, reference indices **40 and
140**, and three selected target frames per trajectory. There are **1,269 target
images** per task. Model-facing images are 512×256; raw RGB and radial depth are
retained at 1024×512 W×H.

The released target index includes **21 targets that equal a reference frame**,
across 19 trajectories. We keep them for the **exact** score. The extra
**HM3D strict** score excludes those 21 targets, leaving **1,248 target images**;
it does not change or rerun the joint groups. Exact/strict here is **not** a claim
about train/test-scene filtering.

2ref1 flattens the same three targets: 1,269 single-query sets. 2ref10 uses the
same trajectories and reference frames and includes the original three targets
plus seven deterministic targets: 423 groups / 4,230 target slots.

## Replica

### Training / old validation

Processed source: `Replica_Bi_train`. The common copy has 250,000 selected groups,
of which 249,000 are training and 1,000 are legacy validation. Some reference
folders supply multiple disjoint target triplets; a logical sample count is not
a count of unique reference pairs or scenes.

There were historical Replica-only continuations, so a checkpoint trained on
Replica cannot be described as zero-shot Replica simply because a later phase
trained on HM3D. Check checkpoint ancestry, not just its latest folder name.
The **current mixed run excludes Replica entirely**, but this does not retroactively
make earlier checkpoints Replica-free.

### New validation: “Replica204”

The regenerated Splatter360-style benchmark uses **68 valid trajectories from
16 scenes**, refs 40/140, **204 targets**. The released index has 77 entries; nine
are too short to contain reference frame 140 and are skipped, matching the
effective loader behavior. The exclusions are recorded in
`evaluation_indices/excluded_invalid_trajectories.json`.

- 2ref3: **68 sets**, 204 targets.
- 2ref1: **204 sets**, the exact same 204 targets.
- 2ref10: **68 sets**, 680 target slots, same refs and three original targets.

“204” means target images, **not 204 three-query groups**. The old 1,000-set
Replica benchmark produces 3,000 target images and is a different evaluation.

## JHU

### Source / processed / training

Original unprocessed panorama JPEGs are in `JHU_ULTRA_360/orig`, organized by
building and capture (`pw`, `ps`); sparse reconstruction folders are not raw RGB.
The scene-split `dataset/images` and `dataset/metadata` feed the processed
`JHU_Bi_data` tree. Our common five-slot data use **`samples_bottom_person`**,
not the generic `samples` render tree.

The held-out unit is a **complete sequence-folder / pose-sequence name**, not an
entire building. For example, holding out `06_AMR1_pw_000000-000066` does not
necessarily exclude another AMR1 sequence. The user intentionally accepted this
sequence-level split. Do not overstate it as building-level or geographically
disjoint generalization.

Ten selected sequences were removed from the original JHU training split.
Remaining data: **697,272 target rows**, regroupable as **232,424 2ref3 sets**,
covering **148 training sequence folders** (158 before exclusion). The current
mixed run selects **40,000 groups**, scene-balanced without replacement, covering
all 148 folders (234–271 groups per folder, respecting availability).

The ten names are in `metadata/jhu_heldout_scenes.json`. This is the authoritative
exclusion list, not `JHU_syncfix_data/val.jsonl` and not simply all entries of the
old common `val.jsonl`.

### Held-out evaluation

`evaluation/jhu_holdout10_500_2ref3` selects **50 groups from each of 10 held-out
sequences**: 500 groups and 1,500 targets. Selected groups have unique reference
pairs within each sequence, three distinct targets and no reference/target overlap.
2ref1 is the exact flattening: **1,500 sets**, not a new random sample.
This test selection is different from the old 1,000-set JHU validation split.

## Perspective / DL3DV

The supplied `dl3dv_points/train` and `dl3dv_points/test` are **prepared DL3DV
2ref3 datasets**, not arbitrary perspective images. They supply two clean refs,
GT targets, target noisy renders, OpenCV w2c poses and **per-view camera
calibration**. Priors were produced with the supplied **VGGT-Omega** process and
GT-reference-pose alignment. They are not ERP PanoVGGT renders.

The camera model has `K`, original `width` / `height` and four distortion
coefficients **`[k1,k2,p1,p2]`**. Images/prior rendering include that distortion;
the ray generator inverts it. Resizing alone or a plain ERP ray map is wrong.
Model-facing resolution is **512×288 W×H**, while stored assets can be larger.

The requested 100k training entries are **97,707 usable unique sets plus 2,293
deterministic repeat entries**, following the original degenerate-set exclusions.
Do not remove those repeats or reintroduce skipped groups when migrating.
`metadata/train_cache/perspective_source_audit.json` records the selection.
The supplied test benchmark contains **2,800 groups / 8,400 targets per task**;
it is not a random holdout generated from our mixed training file.

## Three different meanings of “drop”

1. `cleanup_drop050` in the regenerated HM3D/Replica data means the **precomputed
   50% point-drop render variant** from the two-reference GT-depth renderer.
2. `cleanup_all_drops` expands the precomputed 25%, 50%, 75% variants. It is not
   “all images black” and is not the current PanoVGGT evaluation prior.
3. **Online 2D pixel dropout** is augmentation inside training. It does not modify
   stored render files. Current mixed training uses integer rates 0–100% inclusive
   in its cleanup branch, in addition to a separate 50% all-black-sample switch.

The current paired NVS/cleanup evaluation uses the **same cached raw PanoVGGT
panorama priors / VGGT-Omega perspective priors**, with **no online pixel dropout**.
Do not substitute `cleanup_drop050` just because the task is called cleanup.
